# v1 compatibility profile

This file is the compatibility contract for the current restricted Phase 1
implementation. Anything not listed as supported must be treated as
unsupported, even if an upstream parser, regex engine, or Transformers release
happens to accept it.

## Compatibility matrix

| Surface | Status | Current contract |
| --- | --- | --- |
| Owned normalized Rust tables | Supported | Exact token bytes, a deterministic priority-labeled byte DFA, and a conflict-free ranked LALR table; structural validation is mandatory. |
| Rust source compiler | Supported, restricted | Action-free original Yacc, byte regexes, exact token manifest, conflict-free Pager LALR tables, and default finite output/work limits. |
| Python compiler facade | Supported, restricted | Grammar text or a `Path`, explicit ASCII start rule, terminal list, exact `TokenizerManifest`, and optional ignored terminals. |
| Tokenizer JSON / `from_transformers` | Supported, restricted | A fast tokenizer's `backend_tokenizer.to_str()` must pass the dense ByteLevel profile below; per-token `decode()` and slow-tokenizer introspection are never used. |
| Python base import without Torch | Supported | Torch is optional and loaded only when applying a score mask. |
| Owned `CompiledGrammar.generate` wrapper | Supported, fixed-row | Decoder-only greedy or sampling generation with one beam and one return sequence. |
| Direct `GreatGrammaLogitsProcessor` | Advanced API | Fixed rows and prefixes only; hidden generation modes and ancestry cannot be inferred. |
| Batching | Supported, fixed-row | Nonempty rectangular prompts; row order never changes; batches larger than one require a pad ID. |
| Beam search or row ancestry/forking | Unsupported | `num_beams`, `num_return_sequences`, and `num_beam_groups` must resolve to one; Transformers versions whose unset defaults are `None` are accepted only when `get_generation_mode()` still reports greedy or sampling. |
| Encoder-decoder models | Unsupported | The owned wrapper requires `model.config.is_encoder_decoder == false`. |
| Assisted, contrastive, constrained, prompt-lookup, token-healing, DoLa, or continuous batching | Unsupported | Assistant models, MTP, assistant early exit, `penalty_alpha`, prompt lookup, lexical constraints/forced words, token healing, DoLa, and continuous batching fail closed before a generation session is created. |
| Prepared-grammar serialization or pickling | Unsupported | Prepared caches are derived and remain process-owned. |
| Formal verification | Not complete | Aeneas extraction and handwritten Lean proofs are separate gates; compiler, PyO3, Torch, and Transformers remain outside the theorem. |
| Published packages | Blocked | No project license is selected; crates and Python metadata are explicitly non-publishable. |

## Grammar profile

The compiler accepts the action-free original-Yacc surface understood by
`cfgrammar = 0.15.0`:

- `%token` declarations, one start rule, `%%`, named rules, alternatives, and
  empty productions;
- exactly one `TerminalSpec`/Python `Terminal` for every named Yacc terminal;
- nullable productions and recursive grammars when the generated LALR table
  admits the required finite reduction-progress ranking; and
- an explicit list of ignored lexer terminals. An ignored terminal must be
  declared and must not occur in any production; parser execution treats it as
  a no-op.

The compiler rejects semantic actions, duplicate/missing/unknown terminal
specifications, precedence declarations or `%prec`, every reported
shift/reduce or reduce/reduce conflict and tables without the supported
reduction-progress witness. `lrtable` generates Pager LALR tables, but the
additional ranking requirement can still reject an otherwise valid LALR(1)
grammar. Error recovery, context-sensitive indentation, and runtime grammar
callbacks are not part of the profile.

The Python facade accepts a grammar `str` as source text. To compile a file,
pass a `pathlib.Path` or another `os.PathLike`; a string path is not opened. The
explicit `start_rule` must be an ASCII identifier. It is inserted when the
source has no `%start`, and must equal the source declaration when one exists.
A Python `Terminal` name is also an ASCII grammar identifier, its pattern is a
string, and its priority is an unsigned 32-bit integer.

## Byte-regex and lexer profile

Each terminal is an anchored byte regex compiled into llguidance's shared
`RegexVec`, backed by `derivre = 0.3.12`, with Unicode and UTF-8 modes disabled.
Tested constructs include literal ASCII bytes, `\xNN` byte escapes, positive
byte classes, concatenation, alternation, ordinary grouping, and nonnullable
repetition. This is not a promise to expose every construct accepted by
llguidance, derivre, or `regex-syntax`.

The compiler rejects:

- nullable or empty-language terminals;
- lookaround, noncapturing/flag groups, and other `(?...)` constructs;
- negated/complement classes, including `[^...]`, `\P{...}`, `\D`, `\S`, and
  `\W`;
- anchors and boundary assertions;
- equal-priority terminals that accept in the same reachable DFA state;
- product DFAs above `max_dfa_states`; and
- lexers that would need last-accept rollback across more than the core's
  one-byte boundary protocol.

Smaller numeric priority wins when several terminals accept the same consumed
bytes. Longest matching continues while a DFA transition exists. If a boundary
byte has no transition, the current accepting terminal is emitted and that same
byte is consumed again from a fresh lexer start. Grammars needing buffered
fallback to an earlier accepting prefix are rejected at compile time.

## Exact token manifest

Vocabulary position is the token ID. Each ordinary entry is a nonempty owned
byte string; each EOS entry denotes the single semantic EOS event. The manifest
must be nonempty and contain at least one ordinary entry and one EOS entry.
Duplicate ordinary byte spellings and multiple EOS IDs are preserved as
distinct model-token IDs. NUL and non-UTF-8 bytes are supported.

The Python `TokenizerManifest` takes a byte entry for every vocabulary ID and a
nonempty EOS-ID set. Bytes stored at EOS positions are ignored by compilation.
`TokenizerManifest.from_transformers` accepts only an object exposing callable
`backend_tokenizer.to_str()` returning JSON. The native extractor applies these
checks:

- input is at most 64 MiB and parses as a JSON object;
- `decoder` is one object with `type: "ByteLevel"` and no keys other than
  `type`, `add_prefix_space`, `trim_offsets`, and `use_regex`; decoder sequences
  are rejected;
- `model.type` is `BPE`, `WordPiece`, `WordLevel`, or `Unigram`;
- BPE/WordPiece/WordLevel vocabulary IDs and added-token IDs form one dense
  range of at most 1,000,000 entries; Unigram uses its array position as ID;
- EOS IDs are nonempty, unique, and in range; every special added token must be
  an EOS token; and
- ordinary entries are nonempty and the resulting vocabulary contains a
  singleton spelling for every byte 0 through 255.

For pieces composed entirely of the standard ByteLevel alphabet, the extractor
inverts that alphabet to bytes. A piece containing another character is stored
as that piece's UTF-8 bytes. Added-token fields other than `id`, `content`, and
`special`, plus tokenizer normalization, pre-tokenization, post-processing, and
model algorithms, are not interpreted by the extractor. The Rust
`from_tokenizer_json` API returns a `CompatibilityReport` describing the
inspected model/decoder shape, vocabulary size, EOS IDs, and singleton coverage;
the Python adapter currently returns only the resulting `TokenizerManifest`.
In either case, the caller still owns the end-to-end homomorphism check for the
exact tokenizer configuration. Slow tokenizers, decoder chains, non-ByteLevel
decoders, sparse IDs, non-EOS special tokens, and any profile failing these
checks raise `tokenizer_compatibility`.

Supplying an exact manifest is a trust decision. The caller or a future
compatibility adapter must establish the byte-homomorphism law:

```text
whole_sequence_decode(ids) == concat(manifest_bytes[id] for id in ids)
```

No tokenizer version is auto-whitelisted, and acceptance does not certify
normalizer, pre-tokenizer, post-processor, or added-token context behavior.

## EOS, prompt, and batch semantics

EOS is not an ordinary byte token:

- at logical lexer start it supplies parser EOF;
- at an accepting residual it emits that terminal and then parser EOF;
- at an unfinished residual it is rejected; and
- an EOS token is allowed only when the parser's EOF reduction closure accepts.

The Python prompt is a boundary and is not consumed by the grammar. The first
processor call must exactly equal the captured nonempty rectangular prompt.
Every later call must preserve each complete prior row and append exactly one
token. Row count/order, reuse, and concurrent calls are rejected. One compiled
grammar owns one generation session. The native Python boundary accepts at most
4,096 rows and at most 256 MiB of row-major packed masks per batch.

Generation EOS settings must exactly equal the manifest EOS set. Once a row
accepts EOS, only its configured pad token is allowed; padding is not committed
to the grammar. A multirow batch therefore requires a valid in-vocabulary pad
ID distinct from every EOS ID. The wrapper does not accept an explicit attention
mask, so it rejects the ambiguous `pad_token_id == eos_token_id` case instead of
letting Transformers attend to padded prompt positions. The wrapper installs
GreatGramma last in the supplied logits-processor sequence.

The private native mask is row-major, `ceil(vocab_size / 8)` bytes per row,
least-significant bit first, with one meaning allowed and unused tail bits zero.
The Python Torch layer expands it on the score device and returns an out-of-place
`masked_fill(..., -inf)` result with the original floating dtype, shape, and
device.

| Terminal specifications | 65,536 |
| Ignored terminal names | 65,536 |

| Compiled regex-vector storage reported by `llguidance`/`derivre` | 256 MiB aggregate |
| DFA states validated by core | 1,000,000 |
| Compiler exported lexer-DFA states | 100,000 |
| DFA byte classes | 256 |
| DFA cells | 64,000,000 |
| Parser states | 1,000,000 |
| Terminals / nonterminals | 65,536 each |
| Productions | 1,000,000 |
| Parser action + goto cells | 64,000,000 |
| Logical validated bytes | 4 GiB |
| Validation work | 1,000,000,000 |
| Regex construction fuel | 1,000,000 shared across all terminals |
| Prepared derived items | 64,000,000 per bounded collection |
| Cumulative preparation work | 1,000,000,000 |
| Native Python batch rows | 4,096 |
| Native Python packed batch mask | 256 MiB |

Rust callers may lower these values through `CompileLimits`,
`TokenizerJsonLimits`, `ValidationLimits`, and `PreparationLimits`. The Python
facade currently uses the defaults and bounds EOS collection to the tokenizer
vocabulary ceiling before serializing the backend.

Source-size and grammar-dimension limits are checked before third-party compiler
libraries run. The regex fuel budget covers lexeme registration and is passed to
`llguidance` for the remaining regex-vector construction. `lrtable` does not
currently expose cancellable Pager generation, so parser state, cell, and work
limits apply while copying its completed table; its temporary construction can
precede those checks. Keep the source compiler at an input-trust boundary when
stronger process-level resource isolation is needed.

## Trust and release status

The trusted semantic inputs are normalized token bytes, the already
priority-resolved lexer DFA, the LALR language/table, and its reduction-progress
witness. Core validation checks finite structure, IDs, table shapes, selected
invariants, and budgets; it does not prove those inputs recognize the intended
source language.

The permitted Phase 1 label is **“Aeneas-translatable; Lean proof in progress.”**
It must not be paraphrased as “verified” or “formally verified.” Pinned
source-built Charon/Aeneas extraction, generated-module Lean elaboration, and
byte-drift checking pass; no handwritten soundness or completeness theorem is
included. Compiler generation, tokenizer compatibility, PyO3, Torch, and
Transformers remain outside the planned theorem even after Phase 2.

## Deliberate differences

- GreatGramma Rust uses exact token-local bytes and does not reproduce the
  original per-token decode workaround.
- Corrected logical-start, boundary reconsumption, and EOS behavior follows the
  project contract and Lean fixtures where the paper or prototype differs.
- Longer-context maximal-munch rollback is rejected instead of approximated.
- Parser preprocessing uses conflict-free ranked LALR reduction closure.
- The source compiler reuses llguidance's derivative `RegexVec`; its live
  Earley parser is not this project's runtime algorithm or semantic oracle.
